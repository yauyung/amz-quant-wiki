## 0. 最终 doctrine

**信号先量化，Agent 后解释；先建立“不撒谎”的数据与验证系统，再谈策略增强和自动化。**

OpenAI 提供战略边界：克制、不让 LLM 炒股、不做高频、不急做实盘 long-short。  
Claude 提供执行规程：IC/分层/成本/样本外验证、Alphalens 风格分析、Parquet + DuckDB 工程栈、survivorship 近似方案和明确过关线。

最终采用：**OpenAI 的克制战略 + Claude 的验证规程。**

---

## 1. 不作为核心路径

第一阶段明确不做：

1. **LLM / 多 Agent 直接输出买卖信号**。
2. **高频 / 日内统计套利**。
3. **复杂实盘 market-neutral / long-short**。
4. **主观单股故事驱动选股**。
5. **当前 S&P 500 成分股直接回测历史**。
6. **一开始堆几十上百个因子做 p-hacking**。
7. **把 yfinance + SEC CompanyFacts 伪装成机构级 PIT 数据**。

## 2. 主线配置

| 项目 | 最终选择 |
|---|---|
| 市场 | 美股 |
| 资产类型 | 普通股优先；ETF、preferred、warrant、unit 默认排除 |
| 第一阶段 universe | S&P 500 历史成分近似，用来验证 pipeline |
| 第二阶段 universe | top 500 / top 800 / Russell 1000 高流动性普通股 |
| 再平衡 | 月频 |

## 3. 第一阶段核心因子

### 3.1 纯价格因子优先

1. **12-1 Momentum**
   - 过去 12 个月收益，跳过最近 1 个月。
   - 纯价格，最适合作为第一个 pipeline 验证因子。

2. **Low Volatility / Risk**
   - 过去 60/126/252 日波动率。
   - 后续可扩展 beta、idiosyncratic volatility、max drawdown。
   - 作用：降低动量崩溃和组合波动。

### 3.2 财务因子随后接入

3. **Gross Profitability**
   - `(Revenue - COGS) / Total Assets`。
   - 质量因子的第一代表，Claude 版强调其学术支撑强、字段数量少。
   - 金融股 / REIT 口径不可比，默认先排除或单独处理。

4. **Earnings Yield / Book-to-Market**
   - 价值因子代表。
   - 要注意负值、行业差异、market cap 日期对齐和 SEC tag mapping。

### 3.3 流动性只做过滤/成本

- ADV、Amihud illiquidity、价格下限、成交额下限用于过滤和成本惩罚。
- 第一阶段不把低流动性当 alpha，因为交易成本容易吞掉收益。

---

## 4. 数据原则

1. **原始数据必须落盘**：EDGAR JSON、价格 OHLCV、actions、universe 快照。
2. **财务数据使用可得时间**：优先 `filed` / accession / filing acceptance timestamp，不用 fiscal period end date。
3. **保留 provenance**：至少保留 `ticker, cik, accn, filed, end, form, fy, fp, tag, unit, value`。
4. **CompanyFacts 不是完美 PIT**：可能存在 restatement、taxonomy tag 差异、字段同义映射问题。
5. **survivorship 只做诚实近似**：Wikipedia S&P 500 历史修订 / ETF 持仓 / OSAP 对照，不假装 CRSP 级别。
6. **复权价格**：动量、低波等价格因子必须用 adjusted close。
7. **数据商价格与政策会变**：Tiingo、Polygon、Alpaca 等实施前重新核实。

---

## 5. 验证纪律

### 5.1 正确顺序

1. 单因子 Rank IC。
2. 分位数组合单调性。
3. Factor decay。
4. Turnover。
5. 成本敏感性。
6. FF5 归因。
7. 样本外 / walk-forward。
8. 多因子合成。
9. 组合回测净值。

不要先看漂亮收益曲线再倒推解释。

### 5.2 过关线

| 指标 | 继续研究线 | 良好 | 危险信号 |
|---|---:|---:|---:|
| 月频 Rank IC 均值 | > 0.02–0.03 | > 0.05 | < 0.01 或频繁变号 |
| ICIR 年化 | > 0.3 | > 0.5 | < 0.2 |
| 分层单调性 | 大致单调 | 严格单调 | 非单调/凸型 |
| FF5 alpha t-stat | > 2 | > 3 | < 2 |
| 月度单边换手 | < 50% | < 30% | > 80% |
| 成本后收益 | 必须仍为正 | — | 成本后转负 |

### 5.3 放弃规则

若一个因子在成本后、样本外、分层和 IC 上都不过关，**直接放弃**，不要继续加规则救活。

## 6. 事件/文本增强层

事件层不是主线第一步，放在基础多因子 pipeline 稳定后。

优先顺序：

1. **PEAD / SUE**：盈利公告后漂移；必须用公告日 / filing date，不能用季度末。
2. **SEC filing events**：10-K、10-Q、8-K。
3. **Form 4 insider trading**。
4. **buyback / dividend announcement**。
5. **news density / sentiment**：需付费新闻源或更稳数据后再做。

事件表标准：

```text
(ticker, event_type, timestamp_utc, source, payload, available_at)
```

回测时 T+1 / T+2 才允许使用事件，防止 look-ahead。

---

## 7. Agent / LLM 的边界

Agent 是 process alpha，不是 return alpha。

允许做：

- 候选股解释器。
- 财报 / 10-K / 10-Q / 8-K 阅读器。
- bull / bear thesis 草稿。
- 交易前 checklist。
- 数据异常解释。
- 回测结果总结。
- 交易后复盘。
- 研究日志整理。

禁止做：

- 直接给买卖信号。
- 直接决定仓位。
- 直接下单。
- 在因子打分上游替代统计信号。
- 用叙事结果反向选择因子。

## 8. 12 周研究路线

### 第 1–2 周：数据底座与 universe

- 建 `quant-equity/` 项目骨架。
- 接 yfinance / SEC EDGAR / Ken French。
- 保存 raw + processed 数据。
- S&P 500 历史成分近似或当前成分 + 明确局限。
- DuckDB 查询层。
- 第一份 data QA 报告。

验收：能生成某个月末可复现 universe；能映射 ticker-CIK；能保存 `filed/accn`；能画价格缺失热图。

### 第 3–4 周：基础因子

- 12-1 momentum。
- low volatility。
- gross profitability。
- earnings yield / book-to-market。
- winsorize、z-score、行业中性化。

验收：单因子 Rank IC 和分层收益方向大致符合文献。

### 第 5–6 周：因子验证与 MVP 回测

- Alphalens 风格 IC / quantile / turnover 报告。
- 自建 vectorized 月频组合回测。
- SPY / RSP / QQQ benchmark。
- 单边 10/15/20 bps 成本敏感性。

验收：至少一个或一组基础因子在成本后仍有可解释的正向证据。

### 第 7–8 周：稳健性与归因

- Walk-forward。
- FF5 归因。
- 不同 universe 大小敏感性。
- 不同成本假设。
- 不同 rebalance 日期。

验收：不能只靠某一段时间、某几个票或某个参数成立。

### 第 9–10 周：事件增强

- SUE / PEAD 事件表。
- SEC filing event 表。
- 事件层只作为基础因子组合的增强过滤。

验收：事件时间戳正确；事件增强能改善或解释基础因子组合，而不是替代主线。

### 第 11–12 周：Agent 解释层与 paper portfolio

- 候选股解释 memo。
- 风险 checklist。
- 数据异常解释。
- 每周复盘报告。
- paper portfolio 跟踪。

验收：Agent 不越权，不直接产出买卖信号；只解释量化系统已经筛出的候选。

## 9. 工程执行工作流

用户已确认进入工程阶段，但代码实现采用**问题驱动**，不一次性盲目堆完整系统。

执行规则：

1. 涉及代码实现、重构、测试、工程落地时，优先调用 `claude-code` skill 并交给 Claude Code 执行。
2. 每次调用 Claude Code 前，Judy 需要先和 Blender 确认：
   - 使用的 Claude Code model。
   - 使用的 effort 级别。
   - 本阶段目标与允许修改范围。
3. Claude Code 执行过程中需要按阶段向 Blender 汇报，包括：
   - 阶段目标。
   - 已完成内容。
   - 修改文件。
   - 测试/验证结果。
   - 下一阶段计划或需要用户决策的问题。
4. Judy 负责总控：加载相关 skill、约束任务边界、检查 Claude Code 输出、验证文件和测试结果，再向 Blender 汇报。
5. 第一阶段推荐从小问题开始：数据底座、项目骨架、一个因子、一个验证报告，而不是一次性实现完整量化平台。
